# system-map VS Code拡張

エディタの横に街を並べて、**ビル⇄ファイルを双方向に繋ぐ**拡張。
生成物が単一自己完結HTMLなので、webviewにそのまま載せている。

## 動かす

```bash
npm i                                        # ルートで（three が要る）
code --extensionDevelopmentPath="<repo>/vscode" <対象リポジトリ>
```

または `vscode/` をVS Codeで開いて **F5**（Extension Development Host が立つ）。

アクティビティバーの **System Map** アイコン、またはコマンドパレットから **`System Map: 街を開く`**。

## 表示先

3D都市は横幅が要るので、**既定はエディタの右列**（`ViewColumn.Beside`）。画面の右半分を
使う想定。`systemMap.openLocation` を `sidebar` にすると、アクティビティバーのビューに開く。

ビューは右サイドバー（セカンダリサイドバー）や下パネルへドラッグできるので、常設の列として
置いておける。両方同時に開くこともでき、その場合は同じ街が両方に映って保存でどちらも更新される。

ビューのタイトルバーにボタンが3つ出る。

| ボタン | |
|---|---|
| `$(target)` このファイルのビルへ | 今開いているファイルのビルを選ぶ |
| `$(link-external)` エディタ列で開く | 広く見たいとき |
| `$(refresh)` 解析しなおす | tsconfigのpaths変更や、エディタ外でのファイル増減を拾い直す |

## できること

| | |
|---|---|
| ビルをクリック | 対応するファイルがエディタで開く（フォーカスは奪わない） |
| エディタを切り替え | 対応するビルが自動で選択・ハイライトされる |
| ファイルを保存 | そのファイルだけ再解析して街が更新される（視点・選択・パネルはそのまま） |

開いた時点で街全体が画面に入るようにズームを合わせる（表示先の幅で見え方が変わるため）。
ダブルクリックでその状態に戻る。

設定（`systemMap.*`）で保存連動・エディタ追従・クリックで開く・表示先 をそれぞれ変えられる。

## 構成

```
extension.js     コマンド登録・webview・双方向メッセージ・保存フック
worker.mjs       解析と描画を担当する子プロセス（拡張ホストをブロックしないため）
test-bridge.mjs  VS Code無しでworkerとブリッジを検証する（headless Chrome）
e2e/             本物のVS Codeの中で通しで動かす拡張テスト
```

解析は `createSession()` を子プロセスに常駐させ、保存されたファイルだけ
`session.update()` で再解析する。`cp.fork` は `ELECTRON_RUN_AS_NODE=1` を渡して
VS Code本体（Electron）を素のNodeとして起動している。

webviewに載せる前に CSP を差し込む。three.js が Blob URL を作って動的importするため
`script-src` と `connect-src` に `blob:` を許可している（外部通信は一切しない）。

## 保存したときに起きること

HTMLは作り直さない。**シーンだけ差し替える**。

1. `session.update(file)` — 変更ファイルだけ再解析（数ms）
2. `layout(city)` — Node側でレイアウトを計算し直す（数ms）
3. 前回webviewへ渡した内容と比べ、**変わったノードだけ**をパッチとして送る
4. ページ側の `__applyScene()` が、既存のメッシュを使い回して街を組み直す

3と4が効いている。全体を送ると数百KB、メッシュを作り直すとマテリアルのぶんだけ
シェーダが再コンパイルされて1秒近くかかる。既存メッシュの位置・高さ・色だけ更新し、
端点が変わっていないワイヤは形状も張り直さない。

JIKON（168ファイル）の実測: 送るデータ 245KB → 1KB未満、
シーン組み直し 1067ms → **8〜50ms**。視点も選択も動かない。

## 街が動かないこと

レイアウトは前回の割り当てを引き継ぐ（`layout(city, prev)`）。区画の並び・幅・区画内の
セルを保ち、区画には縦に1〜4行ぶんの余白を予約しておく。枠に収まっているうちは
既存のビルは1棟も動かない。workerが `prev` を持っているので、拡張では自動で効く。

JIKON（168ファイル）で計測（`node src/layout-check.mjs <repo>`）:

| | 引き継ぎなし | 引き継ぎあり |
|---|---|---|
| 1ファイル編集 | 0棟 | **0棟** |
| 1ファイル削除 | 0棟 | **0棟** |
| 48ファイル追加（区画の幅が変わる所まで） | 138棟 (82%) が移動 | **0棟** |

## 検証

```bash
node vscode/test-bridge.mjs <対象リポジトリ>   # VS Code無し（headless Chrome）
node vscode/e2e/run.mjs [対象リポジトリ]       # 本物のVS Codeの中
node src/layout-check.mjs <対象リポジトリ>     # レイアウトの安定性
```

前者は worker のIPC（init/update/scene/render）→ CSP+ブリッジ注入 → ブラウザでの
双方向動作と差分更新（視点・選択が保たれるか、増減が反映されるか）を確認する。

後者は本物のVS Codeを別インスタンスで起動し、コマンド実行・エディタ追従・保存連動を
通しで確認する。対象リポジトリを省略すると使い捨てのフィクスチャを生成する。
（`code --extensionTestsPath` は他のVS Codeが起動していると弾かれるので、
専用の `--user-data-dir` を渡している。`ELECTRON_RUN_AS_NODE` が環境に残っていると
Code.exe がNodeとして起動してしまうので落としている）

## 既知の制限

- ワークスペースの最初のフォルダのみ対象（マルチルート未対応）。
- `tsconfig.json` の `paths` を変えたときは街を開き直す必要がある。
- 予約した枠から溢れるほどファイルが増えると、そこで街全体を詰め直す。
  そのときは大きく動く（頻度は低い）。
- ビルの高さはリポジトリ内の最大LOC・最大fan-inで正規化しているので、
  記録を更新するファイルが現れると全体の高さが少し変わる。位置は動かない。
